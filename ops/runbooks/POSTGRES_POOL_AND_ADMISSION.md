# PostgreSQL pooling and hosted queue admission

The hosted authorization proof recorded own read/write latency around 13–16 seconds. The previous adapter opened a new connection per domain lookup and used an extra savepoint for every SELECT/settings statement. This change reuses at most four backend connections per process, with one warm connection, a five-second checkout timeout and a sixteen-request waiting bound. Transaction-local role, tenant and JWT subject are still set for each operation; no authorization or session result is cached. Automatic prepared statements are disabled for Supabase transaction-pooler compatibility. The pool starts at application lifespan and closes at shutdown.

SELECT and SET statements execute in the outer transaction. Unexpected read errors abort and roll back that transaction. Writes retain their savepoints so an integrity/permission failure can be handled without leaving the caller transaction aborted. Disposable PostgreSQL tests force one shared backend and check tenant/JWT/role reset, absent-context denial and rollback before reusing it for another tenant. These tests do not establish hosted timing or production capacity.

A new hosted analysis is not accepted unless a GitHub source reader exists, the embedded worker is enabled and the tenant is explicitly enrolled through APISHIELD_WORKER_TENANTS. The response is 503 with SOURCE_PROVIDER_NOT_CONFIGURED, WORKER_NOT_AVAILABLE or TENANT_WORKER_NOT_ENROLLED; malformed enrollment is WORKER_CONFIGURATION_INVALID. Existing durable idempotent requests remain replayable. Development/test fixture execution is unchanged. An external worker needs a verified heartbeat admission contract before it can replace this gate; a configuration flag alone is not proof that it is running.

Readiness /readyz remains infrastructure readiness, not GitHub App/product readiness. A configured source reader is likewise not a successful remote installation proof. Enable source reads only with the actual least-privilege App installation and reviewed tenant/repository mapping. Do not enable development fixtures or invent an installation to get a worker success.

Roll back source and FORGEWORKS_RELEASE_SHA together if hosted identity, tenant boundaries or metrics checks fail. Source rollback does not revert database changes. No schema migration is introduced by this change. Hosted performance, cross-tenant authentication and revocation must be remeasured at the deployed candidate; previous release evidence cannot certify changed runtime bytes.
